# To Spec

输入是已经澄清完成的需求共识（对话结论、卡片答案）。把它整理成一份可以指导实现和验收的 Spec，写入当前工作区。

## 输出位置

遵循 `docs/agents/issue-tracker.md` 的约定：

- 文件路径：`.scratch/<feature-slug>/spec.md`
- `<feature-slug>` 用小写字母与连字符，来自功能名称

## Spec 必须包含

1. **背景与问题**：用户遇到的问题，为什么要做。
2. **目标**：这次要达成什么，一句话说清。
3. **范围**：明确要覆盖的场景与明确不做的内容（Out of Scope）。
4. **交互与行为**：关键流程、入口、状态与边界情况。
5. **验收标准**：可以逐条勾选的检查项，写成「当……时，应当……」。
6. **依赖与风险**：外部依赖、已知风险与待确认项（如有）。

## 约束

- 只写文档，不写实现代码，不修改源码。
- 不做新的产品决策；所有内容必须来自已经澄清的共识。仍有歧义时，先调用 `request_clarification`，不要自行补全。
- 写完后确认文件真实存在于工作区，再进入下一步（to-tickets）。
